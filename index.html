Understand your pipeline

JIRA is our source of truth

Every team I've worked on runs off a JIRA board or some Kanban variant.

Tickets don't map 1:1 to merged PRs, but they codify the team-wide process every piece of work goes through, and they illuminate the kinds of inputs that enter our process.

Key question: what are the inputs and outputs of this board, and what are the stages from input to output?

Understand your pipeline

Inputs and outputs

→

Each input is usually a ticket, with zero, one, or many PRs on the way to done.

Epics are big features that need product and system design before being broken down into granular tickets.

Your team's inputs and outputs might be different. It helps to write down how your team's work is managed.

02

Develop an intuition for agents

To speed up the pipeline with AI, we need to understand what we're working with.

Develop an intuition for agents

A coding agent is a for loop

Think, call a tool, add the result to context, repeat.

Until TaskComplete returns true.

You wield a for loop at your fingertips.

When interacting with a coding agent, it helps to understand the underlying code they're running. They are essentially for loops.

Develop an intuition for agents

You set the loop's condition

Frame every request as a condition that is currently unmet, but should be met when the agent is done.

Run many loops in parallel

Spin up worktrees. Name your sessions so you can keep track.

Jason1 Jason2 Jason3 Jason4

Name sessions "Jason1, Jason2, Jason3, Jason4" depending on how many you can manage.

Muse and Grok Bot offer glimpses of new agentic interfaces, but we don't have access, so the metaphor still holds.

Stage 1 · Backlog

Curate your backlog

What lands here:

EpicsBugsPerformance DependenciesCI configDocs Refactoring
  • atlassian-api skill reads and updates JIRA tickets.
  • #product-qa Slack messages automatically become bug tickets.
  • A Confluence design doc gets broken down into prioritized tickets.
  • Ticket descriptions get reformatted for coding agents.
  • /make-ticket captures chores (deps, CI, docs, refactors).
The backlog is the input to your PR machine. Keep its quality high.

Make it as easy as possible to curate, prioritize, and describe the tickets in your backlog.

Chores like updating deps or refactoring usually don't have an explicit user-facing request, so make capturing them seamless.

Stage 2 · Implementation · Loops

Learn to identify loops in your work

1 · What's the condition?

What does "done" look like, concretely and checkably?

2 · How does the agent check it?

Most of the time: how can the agent check its own work?

Give it the right tools (e.g. the gh CLI) and a way to open a PR when done, and it runs autonomously. End every prompt with /draft-pr.

If you can identify, purely as a thought experiment, how the AI could check its work, then with the right skills you can have it run without lifting a finger.

Stage 3 · Tech Review

Human review is the biggest bottleneck

People are busy. PRs wait.

Major system decisions should always get human review, so the system doesn't go off the rails.

But a PR should be quick to review if it:

  • Doesn't introduce new architecture (that's your job)
  • Follows the existing architecture
  • Is modular and isolated
  • Passes static analysis: linters, compilers, Roslyn analyzers, formatters in CI

There's nothing particularly special about a human's feedback for changes that work within an existing architecture.

  • Backlog → implementation → reviewed PR, with no manual intervention.
Stage 4 · Verification

We are all SDETs now

Unity CLI can send taps to the editor and enter/exit Play Mode, so even end-to-end QA can be automated.

  • Tag UI click targets with identifiers.
  • Write feature maps next to prefabs: how to drive them in a standalone Play Mode scene.
  • Pause time and tick it forward in controlled increments.
Screenshot of the preview scene

I don't find true on-device end-to-end verification via computer use valuable. Reserve that for production and product management, since the end-user experience is the one thing that can't be evaluated automatically. That's the whole point.

Takeaways

Treat the JIRA board as your pipeline, then speed up every stage

  • Backlog: manage it with agents.
  • Substrate: lay down architecture for agents to follow.
  • Implementation: prompt with automated success-criteria loops.
  • Review: feed human comments into compounding agent docs.
  • Verification: automate it with end-to-end integration tests.
